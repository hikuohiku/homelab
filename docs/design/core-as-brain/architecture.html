コアを脳にする

判断はコアの常駐セッションに集め、強制は heart のコードに残す。立案を Job からサブエージェントへ移し、着手までの待ちをビート周期ではなく同期呼び出しにする。

支配項は LLM の思考時間ではない。Job 起動・PR・CI・merge・ビート周期という、人間を待たせる必要のない待ちが積み上がっている。立案 Job の中央値 29.8 分のうち、思考以外が半分以上を占める。

迷いどころと、どちらに倒したか

01 — dispatch

「直接」は、直接 Job を作ることではない

コアが k8s Job を自分で作れば、heart が持つ不変条件——すべて実際に起きた事故の対策——を LLM の判断に置き換えることになる。一方で不満は構成ではなく待ち時間だった。

そこで heart に同期の admission gate を足し、コアは MCP ツール dispatch_task で叩く。判定は既存の純関数をそのまま呼ぶので 253 件のテストが効き続け、判定と Job 作成はミリ秒で終わる。人間の待ち時間からビート周期が消え、失うものは無い。

02 — 立案

サブエージェント 2 段のまま移す

opencode 1.18.21 で実測できたこと——サブエージェントは親と別セッションで文脈は白紙、親 bash: deny と子 bash: allow は両立する、そして driver から subtask パートを送れば親 LLM の判断を介さず立案役を起動できる。

つまり「いつ考えるか」は引き続きコードが決められる。judge が別文脈で採点する独立性もそのまま。消えるのは Job 起動と clone のオーバーヘッド、そして発散結果を emptyDir に置いたまま judge の死が道連れにする失敗様式。

03 — 権限

bash を開ける前に、秘密をコアの環境から出す

いまのコアは Telegram・GitHub・NATS の資格情報を環境変数に持つ。bash を開けた瞬間、env 一発で読める。コアは Telegram・GitHub・web という信頼できない入力を読むので、秘密と外部送信経路が同じプロセスに揃う。

だから順序を決める：MCP を子プロセスから別コンテナへ移し、専用 ServiceAccount を与え、automountServiceAccountToken: false を明示する。そこまで済むまで bash は開けない。

「read-only の bash なら安全」は成り立たない——cat /proc/self/environ は読み取りである。守れるのはコマンドの制限ではなく、そのプロセスに秘密が無いことだけ。だから分離が先で、目を渡すのは後（D37）。

コアに何を持たせるか

「何でも見えて操作できる」を 3 段に分ける

段内容判断
見る repo の作業コピー、read-only bash、MCP（k8s・ArgoCD・ログ）、webfetch 全部渡す
作る ブランチ・commit・PR、dispatch_task 渡す　main 直 push は不可のまま
適用する kubectl apply 等のクラスタ変更、PR の merge 渡さない

適用を渡さない理由は不信ではない。merge の条件（CI green ∧ reviewer pass）は機械のゲートであり、LLM の自己申告より強いから。クラスタ変更を Git 経由に縛るのは CHARTER §5 の根幹で、緩めるなら別の意思決定が要る。

段階

前の段が終わるまで次を開けない、という順序そのものが設計の一部

A

秘密を分離する

MCP を別コンテナへ、専用 SA、automount 停止。完了条件：コアの環境変数に長期の秘密が無い。

B

目を渡す

repo の作業コピー、bash、k8s・ArgoCD の read MCP。完了条件：コアが自分で調べて答える。

C

立案を shadow で並走させる

planner と judge のサブエージェントを走らせ、Job 版と採択結果を突き合わせる。完了条件：差分を検分し終える。

D

gate を開ける

heart に admission gate、dispatch_task を active に。完了条件：依頼から着手までが分オーダー。

E

PR を人間の待ち時間から外す

dispatch の正を ops-state へ移し、立案 Job を冷スペアに降格。完了条件：着手が CI を待たない。

まだ確かめていないこと

ここを曖昧にしたまま実装に入ると設計を誤る

  • opencode が remote／HTTP の MCP を受けられるか。　実測で確定（2026-08-24）——1.18.21 は type: "remote" を受け、localhost の別コンテナに繋がる。MCP が死んでも core は生き、そのツールだけが消える。ただし接続状態は自動更新されず自動再接続も無いので、サイドカー再起動後に POST /mcp/<name>/connect を叩く仕掛けが要る。
  • コンテキスト上限に達したときの実挙動と compaction.auto の既定値。常駐セッションの寿命がここで決まる。
  • 子セッションのトークンは親に合算されない。D36 で強制はしなくなったので、表示のためだけに GET /session/{parent}/children を足す価値があるかを決める。
  • subagent_depth の既定は 1。孫を呼ばせるなら明示設定が要る。
  • permission のマッチ無しは ask に落ちる。headless では応答できる者が居ない。使うツールを全列挙して書き切る——CHARTER §5.1 が「ask を新設しない」を定めた事故と同型。
  • 常駐セッションが誤った思い込みを抱えたまま長期化するリスク。日次で切り直し、状態は記憶ではなくツールで読み直す運用を併せて決める。

決定記録

rev3。既存の D1〜D27 のうち 2 つを差し替える

D28D2 を差し替える。「選定はコア、起草は Job」→ 起草もコアのサブエージェント。Job は実装にだけ残す。起草の待ち時間が Job 起動・PR・CI に支配されており、思考時間ではないため。
D29D7 を差し替える。「コアは K8s write を持たない」→ コアは dispatch を同期で要求できる。ただし Job を作るのは heart のままで、k8s の write 権限は渡さない。強制点を増やさない。
D30D3 は維持。コアは git に書かない。ブランチと PR は作れるが、ops-state への commit は heart 単独。
D31実装は Job のまま。runner をサブエージェント化しない。中央値 21 分・最長 8 時間の作業を常駐セッションに載せると、Pod の生存と作業の生存が結合する。
D32dispatch の正は ops-state。採択 spec の読み先を main の archive.jsonl から ops-state の projects.json へ移す。改竄耐性はむしろ上がる——main は CI を通る PR なら誰でも書けるが、ops-state は heart しか書けない。
D33bash の前に秘密を出す。MCP を別コンテナに移し、専用 SA を与え、automount を止めるまで bash を開けない。
D34ask 禁止。サブエージェントの permission は使用ツールを全列挙する。
D35冷スペアを残す。立案 Job の経路は消さない。コアが応答しないときは heart が従来どおり Job で立案する。
D38分離が縮めるのは境界であって、消すのではない。秘密をサイドカーへ移すと core の環境変数からトークンは消えるが、bash を持つ core は 127.0.0.1 のサイドカーへ直接 JSON-RPC を投げ、公開されたツールを呼べる。境界は「生のトークンで API を叩き放題」から「サイドカーが公開したツールの範囲内」へ縮むだけ。次の論点はサイドカー側のツール設計——宛先の固定、レート制限、スコープの最小化。
系として、MCP の headers に秘密を置かない：GET /config は展開後の値をそのまま返すので bash からは丸見え。同一 Pod の localhost はネットワーク名前空間が境界なので、そもそもトークンが要らない。
D37秘密の分離を「目を渡す」より先にする（自己訂正）。当初は Phase A で read-only bash を含む目を渡し、Phase B で秘密を分離する順にしていたが誤り。read-only の bash でも cat /proc/self/environ で環境変数は読める——コマンドを制限しても秘密は守れない。守れるのは「そのプロセスに秘密が無いこと」だけなので、分離を先に置く。
D36予算方式を廃止する。opencode Go の定額へ完全移行したので、金額とトークンで仕事を止めるのをやめる。計測は残し、強制をやめる——breaker・soft cap・budget_exhausted を落とし、通知の日次上限（人間の注意力の予算）と max_sessions_per_project（無限ループの最後の歯止め）は残す。
帰結として、上限待ちが異常ではなく通常の運転状態になる。QUOTA_WAIT_MAX_ROUNDS = 6 はビート周期に依存して意味を持たないので、連続 24 時間の壁時計に置き換える。これをやらないと廃止そのものが大量 stall を生む。
実測の出典：ops-state の audit.jsonl（立案 44 サンプル・runner 110 サンプル）、projects.json、2026-08-24 の Telegram 依頼 1 件の追跡、opencode 1.18.21 のローカル実測と OpenAPI。
