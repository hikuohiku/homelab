## §2 実行サイクル — immich バックアップの実在確認 (T-0068)

issue #56, 2026-08-05 12:35:47 の指摘。T-0068 は immich 内蔵の日次 DB ダンプが
`UPLOAD_LOCATION/backups/` に落ちている前提だったが、これはソースコードで確認しただけで実機で見て

という教訓から `pvc_usage` の immich エントリに `backup_listing` を追加して実在確認できるようにした
（T-0068 フォローアップ, run #49）。

## §4 共通ルール — stale なローカル main から分岐 (run #72)

run #72 の実例。直前の起動が作った PR を merge した直後に別ブランチを切ったところ、ローカル `main` が
merge 前のままだったため、その merge コミットに含まれていた `ops/backlog.json`/`ops/journal/*.md` の

原因だった。

## §4 共通ルール — Job Force=true/Replace=true を2回踏んだ話 (T-0108/T-0111)

この問題は T-0108 と T-0111（run #75, #250-#254）で 2 回独立に踏んでおり、後付けで気づくたびに
1 起動分の待ち時間（ArgoCD の sync 検出込みで数分）を無駄にしている。内容が変わりうる Job リソース
（検証用 Job など、同じ名前のまま再実行・再検証するもの）に最初から `Force=true,Replace=true` を
付けておかないと、`.spec.template` が不変フィールドのため 2 回目以降の変更が `field is immutable`
で失敗し ArgoCD が `OutOfSync` のまま固まる。

## §4 縛る変更 — immich memory limits の revert (T-0055/#134)

issue #56（2026-08-05 02:50:59, 02:55:16）の指摘。`CI が green` は「壊れていないこと」の証拠であって、
「その値が妥当なこと」の証拠にはならない。T-0055（immich の memory limits）が実例: 値の根拠が immich
自身の実測ではなく「他コンポーネントの requests 合計」で、足りなければ OOMKill で Pod が死ぬのに、
このクラウドサンドボックスはクラスタに到達できず観測できなかった。issue #56 側で発見され `#134` で
memory limits のみ revert された（requests と CPU limits は残置。CPU limits は超過しても throttle で
回復するため）。
